# Explicit operator ensure

`nightscout admin ensure` is a separate audited operator capability. It creates a fresh tenant through ordinary provisioning or repairs two provenance-backed kinds of missing metadata. It preserves clinical data, credentials, revocations, progress, history and lifecycle claims. It performs no factory reset or interrupted-restore resume.

This source capability supports an unselected admin process only. An installed connection-admission profile refuses before ensure construction or dispatch. It has no selected host/control port. Source and recording tests do not establish PostgreSQL/Vault native qualification or whole-candidate acceptance.

## Preparation and authority

Prepare the new `lib/tenant-registry/ensure-candidate.json` catalogue in a separate schema through the explicit operator migration workflow. Assign its objects to the deployment's non-login, non-superuser, non-bypass catalogue owner. Apply `lib/tenant-registry/ensure.js` `grants()` to a distinct login identity. It receives fixed proof reads, append-only operation audit INSERT, and reconstruction INSERT on current settings and registry public-key metadata. It receives USAGE, without UPDATE/ownership, on the ledger identity sequence; no extra index or summary table is added. It receives no credential/clinical writes, ciphertext SELECT, history UPDATE/DELETE, schema creation or role management. The endpoint performs no DDL. Missing schema/grants or altered provenance/trigger/validator objects refuse preparation.

Run ensure in a dedicated unselected admin process, optionally with its ordinary fresh provisioning/inspect service. The parser rejects ownership, pool operations, connector and management-session services in that process. Its proof identities have SELECT(tenant_id) on clinical tables and are therefore real clinical actors to the existing restore census. Finish ensure, stop/drain this dedicated process, and let authoritative restore preflight prove those server backends absent before restore. A local close or pool.end is not retirement evidence; uncertain backends remain a refusal. This first capability does not coexist with restore and adds no census exemption.

Add an optional `ensure` section to `MULTITENANT_ADMIN_CONFIG`, as published in `lib/server/serve/plan-contract/schema/admin.schema.json`. It has provisioning's namespace/checkpoint/mode/operator grammar plus `ledgerNamespace`, a distinct `connectionEnv` for the narrow ensure identity, and a read-only Vault metadata credential. Provisioning's existing write-capable SQL/Vault identities remain separate. When ordinary `provisioning` is also composed, its namespaces, checkpoints, mode, owner catalogue and Vault origin/mount must match ensure. If it is absent, registered repair still works but fresh creation refuses.

Fresh creation also requires the closed deployment-only `dependencyNamespaces` map, with bounded namespace instances and canonical/socket-order enum choices from the actual source families. It covers clinical data/counters, both checkpoint instances, human sessions, suppression/outbox, policy/owner authority, all current/history/audit/deletion/progress records, registry and ensure ledgers. Missing/unknown/mismatched maps refuse before key birth; API callers cannot supply one. The supported profile places every canonical durable instance in the same observed PostgreSQL database. External/unknown/multiple-database and legacy-unfenced writer profiles are unsupported. A targeted subject-administration audit tenant index is the only new control-plane index; no clinical ingestion index is added. Actual canonical schemas, forced RLS/tenant policy, valid tenant-leading indexes or validated non-null tenant-preserving FK chains to empty indexed parents are screened. An unknown tenant_id relation refuses. No clinical/ciphertext values are read for dependency proof.

Upgrade all admin/provisioning writers together before enabling ensure. The new shared nonblocking session fence is taken by both updated entry paths before the fresh predicate and key creation. Older running provisioners ignore this fence; a mixed writer fleet is unsupported. The refactor uses one existing admitted provisioning client across its read-only transaction, bounded Vault step and write transaction. It adds no client slot or admission credit. Fresh creation additionally takes the existing derived tenant lifecycle key exclusively on that same session, rechecks the full predicate, and retains the lock through Vault and write commit. Already admitted shared clinical/credential operations cause busy before key creation. Registered retries do not take that fresh exclusive lock. Only coherent writers using the canonical lifecycle fence are covered.

## Requests and outcomes

The private admin plane accepts `POST /v1/tenants/{id}/ensure`. Its closed published `TenantEnsureRequest` contains `operationId`, `id`, `hosts` and optional `internalHost`. No caller-supplied proof, key/role names, SQL, credential or reset field is accepted. The route remains absent from tenant-admin, DATA and internal RPC composition. This private operator plane keeps the deployment-controlled access model of provisioning; it does not add a public authentication surface.

CLI form: `nightscout admin ensure --id <tenant UUID> --operation-id <operation UUID> --host <alias> --url <private admin origin> [--json]`. Canonical-internal mode uses `--internal-host`; the actual configured mode decides valid host combinations. The CLI carries no SQL/Vault credential and validates the entire published response before printing it.

The result contains only the tenant/operation IDs, outcome, fixed code and bounded changed-object names. `complete`, `created` and `repaired` exit 0; definite refusal exits 1; `unknown` or unavailable/unexpected peer output exits 69; usage exits 64. Responses use no-store. Key material, root secrets, ciphertext, provider diagnostics and backend URLs are absent. Fresh ensure never requests or persists the creation-only root-secret response of ordinary provisioning.

Actual database identity is observed, not inferred from URLs: each PID is checked against its own client, then database name/OID, server address/port, postmaster birth and cluster lineage are compared across the two prepared identities. The actual provisioner reobserves before key birth/write/commit. Endpoint/postmaster changes refuse until the dedicated admin is restarted and state reconciled; there is no automatic adoption or credit refund.

A successful operation ID replays its recorded result without another key read or mutation. A different normalized request with the same ID conflicts. A concurrent local attempt returns busy before queuing another ensure checkout; busy/invalid ingress refusals are not accepted mutation intents. Accepted intents and conclusive results are append-only records, with fixed actor identity from configuration. Safe operation/outcome/code counts are logged. A later repair after a conclusive refusal needs a new operation ID.

## Conservative repair matrix

| Observed state | Action |
| --- | --- |
| No registry entry and no partial provisioning rows or host conflict | The actual fresh provisioning entry takes the new fence and rechecks its complete predicate. Existing key residue is adopted by that fresh operation. |
| Registered tenant with any missing key | Refuse dependency-unknown; restore the original key from backup. Never create fresh material, even when a current credential/ciphertext table is empty. |
| Wrong key type or mismatching recorded public key | Refuse mismatch; never overwrite either side. |
| Missing current settings, complete trustworthy immutable versions 1 through N | Restore the exact version-N document under the lifecycle and policy fences, in the same transaction as the result audit. Keep every history row unchanged. |
| Missing public-key registration, intact version-1 key and a latest successful immutable ensure observation of that exact purpose/kid/type/version/public key | Reinsert only that registration. The first ensure observation cannot retrospectively prove an already missing registration. |
| Other missing current row, missing progress, interrupted restore/deletion, unfinished operation, removed tenant or incomplete provenance | Explicit refusal. No initial defaults, generation1, unrevocation, claim clearance or lifecycle reopening. |

Settings completeness uses scalar count/min/max over the tenant's indexed history and reads only one size-bounded latest value. It never returns all historical values to the process. The operation lookup returns at most three bounded rows (two valid phases), and only the latest successful key observation is returned, capped at 4096 bytes and ordered by the immutable ledger identity rather than wall-clock time. Vault key metadata has a fixed 65536-byte reply bound, enforced incrementally before UTF-8/JSON allocation. Existing keys with metadata larger than that now refuse inspection/provisioning/ensure as unconfirmed; there is no unbounded compatibility fallback. Overflow or unavailable provenance refuses; there is no inferred proof or global tenant scan. The retained per-tenant aggregate scan cost is explicit.

## Failure and uncertainty

An intent commits before any fresh key work. Fresh provisioning owns its existing PG transaction and key residue semantics. Registered repairs and their completion audit share one PG transaction; sequential independently committed repair calls are not used. Missing settings retain their historical version, and key/credential generations are never reset.

Vault and PostgreSQL have no joint atomic transaction. A lost query/commit response produces an unknown outcome with the same operation ID; no plaintext secret is saved for replay and no key is deleted as rollback. Retry re-reads the ledger and current admitted state. An unresolved intent refuses further fresh key birth, including under a new operation ID; reconcile it explicitly before another creation attempt. It may establish current completeness, but it does not claim the earlier ambiguous commit was proved rolled back. A committed result is replayed only through its exact correlated closed shape.

Checked-out clients have an owned first-error bridge while Vault is awaited. Each query and external await checks that first failure before and after continuation. Failure stops subsequent key requests and commit, and passes the error to the actual pool. The bridge stays installed through release and is then removed. Local end, a business SQLSTATE or a client timer is never used as server-retirement, ReadyForQuery, acknowledgement or credit evidence; the existing admission wrapper remains the only such authority.

Focused source controls are in `tests/tenant-ensure*.test.js`. Native least-privilege PG/Vault, concurrent process, crash/recovery and selected-host qualification remain separate measured boundaries. Factory reset remains a separate operation and is not implemented here.

Each key operation has one absolute configured deadline across credential retrieval, provider fetch, body cancellation and all GET/POST/read steps. Expiry prevents undispatched continuation even when a provider ignores cancellation; it does not prove a dispatched write was rolled back.
