## Required backend sampling versus shared front-end coverage

Two **backend-dependent composition vectors remain UNMEASURED**: adversarial fully tied entries paging, and the supplier-agnostic importer algorithm combined with the real PG target through an interrupted later page and rerun. Existing ordinary pagination, pure importer and native target assertions remain credited. No concrete missing accepted product capability was found; a failing native vector must stop and identify the mechanism rather than earn a new waiver.

Canonical front-end coverage is separate. The native profile/food case above already compares API3 JSON/CSV/XML parsed bodies and content headers, 406 and suffix handling against Mongo. Shared validation/parser/purifier code also has native domain and representative entries coverage. A literal entries XML/CSV matrix or exhaustive duplicate entries copy of every generic treatment input vector is not invented as another M1 prerequisite. Optional representative entries boundary sampling can share the existing CRUD fixture. The JSON retains exact source declarations so unassigned entries-specific behavior remains visible, not silently green.

The importer contract intentionally accepts a source supplier. Its missing native composition vector can use deterministic callbacks; no external source HTTP server, CLI, authentication transport or lifecycle is required. The expected boundary is **committed earlier pages retained, interrupted page rolled back**, followed by an idempotent restart from the beginning. No whole-import atomicity is claimed. Hourly retention retry/log scheduling and numeric performance budgets remain outside this M1 backend disposition.
